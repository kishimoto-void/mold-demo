# Bottom Mold — 基底評価・許容仕様

**文書種別:** 規範仕様 / Mold Specification  
**対象実装:** `bottom_mold.py` v0.1  
**仕様版:** v0.2-draft（レビュー反映案）  
**状態:** 設計レビュー中  

---

## 1. 目的

Bottom Mold は、上位の Persona Seed・Process Mold・タスク仕様から渡される評価方針について、次の2つを混同せずに扱うための共通基盤である。

1. **パーソナライズ評価:** 個人の好みやタスク上の目標に照らし、プラス方向・マイナス方向の変化を許容して観測を保持する。
2. **厳密評価:** 明示された規則・条件・正答基準への適合を判定する。

Bottom Mold は、どの応答が好ましいかを単独で決定するのではない。上位の仕様で定義された評価軸を受け取り、観測・分類・厳密チェックを分離して扱う。

> **中核原則:** パーソナライズ上の好みで、厳密な正誤条件や事実性の基準を変更しない。

## 2. 設計原則

### 2.1 評価軸の分離

パーソナライズ評価と厳密評価は、独立した評価経路として扱う。パーソナライズ結果の好悪・スコア・方向によって、厳密チェックの結果を上書きしてはならない。

### 2.2 ブレを許容し、観測を保持する

パーソナライズ領域では、当初の期待からの逸脱を一律にエラーとはみなさない。プラス方向とマイナス方向の両方を記録し、失敗・不一致・寄り道を次の判断に役立つ情報として保持できるようにする。

### 2.3 `≌` は相殺ゼロではない

`≌` は、**暫定的なニュートラル／未確定の均衡**を表す記号として用いる。正負の観測を足し引きしてゼロにすることや、すべての問題が解決したことを意味しない。

- 正負が混在する場合は、それぞれの観測を保持したまま `≌` と分類できる。
- 方向を判定できる観測がない場合も、結論を急がず保留できる。ただし、**観測がないことと、正負を観測したうえで均衡していることは意味上区別する**。
- `≌` は永続的な確定値ではない。新しい情報によって再評価できる。

### 2.4 方向と価値を混同しない

`+` は指定された評価軸に沿ったプラス方向、`-` はマイナス方向を表す。方向だけから、真偽・道徳性・全体的な品質を判断してはならない。

例：説明が短くなったことは、簡潔さの軸では `+` でも、詳細さの軸では `-` になり得る。評価軸は上位仕様で明示する。

### 2.5 根拠と仮説を分ける

評価には判断理由を付ける。観測済みの事実、推論、仮説、本人の好みを可能な範囲で区別する。確かめていない事柄を確定した事実として扱わない。

## 3. 評価モード

### 3.1 Personalization Mode

個人の好み、対話スタイル、探索の有用性、タスク目標への適合などを評価するモード。

扱う値：

| 記号 | 意味 | 運用 |
|---|---|---|
| `+` | プラス方向の変化 | 観測と根拠を保持する。これだけで全体が成功したとは断定しない。 |
| `-` | マイナス方向の変化 | 観測と根拠を保持する。直ちに探索を打ち切る理由とはしない。 |
| `≌` | 暫定ニュートラル／未確定 | 正負混在や判断保留を表す。相殺や完全解決を意味しない。 |

分類の基本方針：

| 観測状況 | 分類 | 意味 |
|---|---|---|
| `+` のみ | `POSITIVE_DRIFT` | プラス方向の観測がある |
| `-` のみ | `NEGATIVE_DRIFT` | マイナス方向の観測がある |
| `+` と `-` の両方 | `MIXED_PROVISIONAL_NEUTRAL` (`≌`) | 正負の両方を残した暫定状態 |
| 方向を判定できる観測なし | `NEUTRAL_OR_UNCHANGED` (`≌`) | 方向を確定できる情報が未観測。均衡が実証されたわけではない |

**v0.1 の注意:** `DeviationDirection.NEUTRAL` を明示的に観測した場合と、観測が空の場合が同じ `NEUTRAL_OR_UNCHANGED` に分類される。両者を区別したい用途では、現行実装だけでは意味情報が不足する。v0.2 では「明示されたニュートラル観測」と「観測不足」を別状態として扱うことを推奨する。

### 3.2 Strict Mode

数学・形式的条件・教育問題・データ形式・明示された受け入れ条件など、正誤判定の規則が定義されている領域で使用する。

例：整数の通常の算術では `1 + 1 = 2`。期待値と実際の値を、指定された規則で比較する。

運用要件：

- 判定対象と判定規則を明示する。
- 条件を満たす場合は `PASS`、満たさない場合は `FAIL` とする。
- パーソナライズ上の好みや会話上の満足度で `PASS` / `FAIL` を変更しない。
- 規則や前提自体が曖昧な場合は、誤った厳密さを装わず、定義の確認を要求する。

**実装上の範囲:** v0.1 の `require_exact_equality` は `actual == expected` による等値比較を行う汎用的な入口であり、任意の数学的証明、浮動小数点の許容誤差判定、すべての形式的検証を自動で実行するものではない。

## 4. 逐次更新モデル

Bottom Mold は逐次更新を**許容する**が、v0.1 の Python 実装が自律的な学習や更新ループそのものを実行するわけではない。現在の実装は、渡された観測を分類し、記録を返す参照実装である。更新を実行する主体は上位のオーケストレーターまたは利用者とする。

推奨フロー：

```text
目的・評価軸を受け取る
        ↓
結果やフィードバックを観測する
        ↓
観測を + / - / ≌ と根拠に分けて記録する
        ↓
正負の観測を相殺せず保持する
        ↓
必要に応じて仮説・優先順位・処理方針を更新する
        ↓
再評価する（厳密条件があれば独立して再チェック）
```

更新時の規則：

1. 失敗した試行から得られた情報を、可能な範囲で残す。
2. 新しい証拠が出たときは、以前の仮説を修正できる。
3. 不確実な状態を、見栄えのよい単一スコアへ強制的に縮約しない。
4. 更新によって不変条件や厳密な判定基準を弱めない。
5. 記録された過去の観測と、現時点の判断を区別する。

---

## 5. 不変条件（Invariants）

以下はパーソナライズ設定では変更できない基盤ルールとして扱う。

1. 根拠・観測・推測・仮説を混同しない。
2. 未確認の事実を捏造しない。
3. パーソナライズの好みで厳密な正誤条件を変更しない。
4. 正負の観測を、理由なく相殺または破棄しない。
5. 観測不足を、確定したニュートラルや成功の証明として扱わない。
6. 上位仕様と厳密条件が衝突した場合は、衝突を隠さず明示する。

これらは評価のための事前条件であり、通常の `+` / `-` の評価対象に混ぜない。

## 6. v0.1 実装との対応

| 仕様要素 | 現行実装 | 制限・注記 |
|---|---|---|
| 評価モード分離 | `EvaluationMode` | `PERSONALIZATION` と `STRICT` を用意 |
| 正負の方向 | `DeviationDirection` | `+` / `-` / `≌` |
| 観測の保持 | `PersonalizationResult.observations` | 方向が混在しても全記録を保持 |
| 正負混在時の暫定分類 | `MIXED_PROVISIONAL_NEUTRAL` | 単純相殺しない |
| 観測なしの分類 | `NEUTRAL_OR_UNCHANGED` | 明示的 `≌` と空観測を区別しない点が既知の制限 |
| 変化の大きさ | `magnitude` | 現行では保存・非負検証のみ。分類や集約には利用しない |
| 厳密チェック | `require_exact_equality` | `==` の等値比較。汎用証明器ではない |
| 整数加算の例 | `check_integer_addition` | `1 + 1 = 2` の参照例 |
| 自動逐次更新 | 未実装 | 上位レイヤーが観測追加・再評価を制御する |

## 7. API と型安全性に関するレビュー方針

### 7.1 モード別 API を主経路にする

モードによって必要な引数が異なるため、上位コードからは次のメソッドを直接呼び出すことを推奨する。

- `evaluate_personalization(observations)`
- `require_exact_equality(expected, actual, rule)`

現行の `evaluate(...)` は便利な振り分け API として残せるが、`strict_expected=None` などのデフォルト値により必須引数の欠落を呼び出し時まで発見しにくい。次版ではモード別の入力型や専用リクエスト型を検討する。

### 7.2 `magnitude` の意味を限定する

v0.1 では `magnitude` を記録用メタデータとする。尺度・単位・比較可能性・閾値が定義されていないため、平均化、重み付け、状態判定に使用しない。

異なる尺度の `magnitude` を、定義なしに加算・比較してはならない。将来使用する場合は、尺度名・単位・基準・適用範囲を先に仕様化する。

### 7.3 厳密比較の拡張

`require_exact_equality` は厳密条件の最小例である。将来、任意の述語や専用バリデーターを受け取る API に拡張する場合でも、判定規則が明示され、失敗理由が追跡可能であることを条件とする。

## 8. 最低限のテスト要件

次のケースをユニットテストとして固定する。

- `+` のみなら `POSITIVE_DRIFT`。
- `-` のみなら `NEGATIVE_DRIFT`。
- `+` と `-` の混在なら `MIXED_PROVISIONAL_NEUTRAL` となり、両観測が保持される。
- 空観測は `NEUTRAL_OR_UNCHANGED` となり、成功・確定均衡を意味しない。
- 根拠が空文字または空白だけなら入力エラー。
- `magnitude` が負なら入力エラー。
- `magnitude=None` は許容される。
- `1 + 1 = 2` は `PASS`。
- `1 + 1 = 3` は `FAIL`。
- `bool` を整数として受け入れない。
- パーソナライズ結果によって厳密チェックの結果が変更されない。

## 9. 次版の優先順位

### P0 — 意味の曖昧さを減らす

1. 明示的な `≌` 観測と観測不足を別状態にする。
2. `evaluate(...)` のモード別引数を型で表現し、必須項目の欠落を早期検出する。
3. 上記の最小ユニットテストを追加する。

### P1 — 記録品質を上げる

4. 観測の種類（実測・ユーザー反応・推論・仮説）を構造化する。
5. `magnitude` の利用目的が決まるまでは、記録用に限定する。
6. 各観測に評価軸や時点を付ける拡張を検討する。

### P2 — 連携を増やす

7. 上位の Persona Seed / Process Mold と接続する入力スキーマを定義する。
8. モデル別アダプターの出力要件と、実行後の評価記録を分ける。
9. 保存する記録とユーザーが制御できる記録の範囲を定義する。

---

## 10. 非目標と限界

Bottom Mold は、以下を直接保証するものではない。

- LLM 内部の思考や計算過程を直接制御すること。
- 回答の正確性を自動的に完全保証すること。
- 観測だけからユーザーの真の好みを確定すること。
- v0.1 の `magnitude` を使って客観的な総合スコアを算出すること。
- 観測分類だけで長期記憶やモデル自体の学習を行うこと。

本仕様は、モデルの内部動作を主張するものではなく、上位システムが評価・更新方針を実装するための外部契約である。

## 11. 一文定義

> **Bottom Mold は、パーソナライズ領域では `+` と `-` のブレを観測として保持し、必要に応じて `≌` という暫定状態を許容する一方、厳密性が必要な領域では明示された規則による検証を独立して要求する共通基盤である。**
