# Middle Learning Mold — 共通学習プロセス・モールド

- **Version:** 0.1.0
- **Status:** Prototype / reference implementation
- **Files:** `middle_mold.py`, `MIDDLE_MOLD.md`
- **Primary role:** LLM が学習支援を実行する際の、人格に依存しない共通プロセス基盤
- **Language:** Documentation in Japanese; identifiers and contracts in English

---

## 1. 概要

Middle Learning Mold（以下、Middle Mold）は、学習用途の LLM システムにおいて、学習方法の選択・実行順序・適応条件・評価・終了報告を定義する中間層である。

Middle Mold の目的は、特定の人格や特定の教科に最適化することではない。学習科学の知見を参考にしながら、複数の用途で再利用できる共通の学習プロセスを提供することにある。

Middle Mold は、学習者の性格、口調、価値観、個性、関係性を定義しない。学習者へのパーソナライズは Persona Seed などの独立した層に置く。何を学ぶか、何を達成すべきかという目的は Purpose Program などの独立した層に置く。

概念上の構成は次のとおり。

```text
Human / Operator
       |
       v
TOP: Purpose, goal, context, constraints
       |
       v
MIDDLE: Middle Learning Mold
        - method selection
        - learning sequence
        - adaptation rules
        - evaluation contract
        - exit report
       |
       v
BOTTOM: LLM
        - interprets the contract
        - performs tutoring interaction
        - records observed results
       |
       v
Output / Exit Report
```

用途に応じた全体像は次のように表現できる。

```text
Persona Seed + Purpose Program + Middle Mold + LLM
                         |
                         v
                 Purpose-specific use
```

この式は、単純な加算や数学的な同値式を意味しない。各層の責務を分離して組み合わせるという設計上の表現である。

---

## 2. なぜ Middle Mold が必要か

一般的な学習用プロンプトでは、目的・人格・説明スタイル・教材・学習方法・評価方法が一つの指示文に混在しやすい。その状態では、用途を変更するたびに学習方法まで書き直したり、人格の変更によって学習手順が意図せず変化したりする可能性がある。

Middle Mold は、これらを分離する。

### 2.1 分離する責務

| 層 | 責務 | 原則として持たせないもの |
|---|---|---|
| TOP / Purpose | 達成目標、対象範囲、期限、利用条件、制約 | 汎用学習方法の全仕様 |
| Persona Seed | 個別化、対話上の好み、支援の調整 | 学習効果を左右する共通手順の独占 |
| Middle Mold | 学習方法の選択、順序、適応、評価、報告 | 固有の人格、特定個人の価値観、教科固有の正解集 |
| BOTTOM / LLM | 契約の実行、説明、質問、採点補助、観察記録 | 根拠のない結果の捏造、未確認の習熟認定 |
| Domain Content | 教科・職務・技能の内容、教材、正答基準 | 学習者の人格定義 |

実装環境によって TOP / Persona Seed / Purpose Program の配置や名称は変えてよい。ただし、責務を混ぜないことが重要である。

### 2.2 Middle Mold の中立性

Middle Mold は、次のような設計を採用する。

- 学習者の個性を固定しない。
- すべての学習者に同じ難易度・同じ説明量を強制しない。
- 個別化は外部の Persona Seed や学習者プロファイルと接続できるようにする。
- 目的の変更に対して、目的に合う方法を再選択できるようにする。
- 方法の採用理由と不採用理由を明示する。
- 観察できていない能力や学習成果を推測で確定しない。

「共通基盤」とは、すべての場面で同一の学習手順を無条件に実行することではない。共通の選択規則と検証規則を使い、状況に応じて手順を構成することを指す。

## 3. 設計原則

### P1. Purpose と Method を分離する

目的は「何ができるようになる必要があるか」を定義する。Middle Mold は、その目的に到達するためのプロセスを選択する。

例：

- Purpose: 2か月後のテストで因数分解問題を解けるようにする。
- Middle Mold: 事前診断、例題、段階的演習、想起練習、誤り修正、間隔を空けた復習を構成する。
- Domain Content: 対象範囲の式、解法、正答条件を提供する。

### P2. Persona と Method を分離する

説明を短くする、比喩を増やす、対話を多めにするなどの個別化は Persona Seed 側で扱える。ただし、個別化によって評価基準を勝手に甘くしたり、未達成を達成済みにしたりしてはならない。

### P3. 手法は無条件に全部使わない

想起練習、分散学習、交互配置、例題学習などを常に一括で適用するのではなく、目的・既有知識・期限・課題特性に応じて選択する。

例：

- 初見の複雑な手順：最初に例題とガイド付き練習を置く。
- 類似した問題形式の判別：基本手順を学んだ後で交互配置を検討する。
- 試験が目前：広い範囲を新規学習するより、代表問題の想起と高頻度エラーの修正を優先する。
- 習熟が不明：短い診断から開始する。

### P4. 学習成果と自信を分ける

学習者が「分かった」と感じることと、独力で再現できることは同一ではない。自信は記録してよいが、正答や独立遂行の代替指標にしてはならない。

### P5. 適応は観察結果に基づける

同じ誤りが続いた場合は説明の言い換え、表現の変更、前提知識の確認などを検討する。成功が安定した場合はヒントを減らす。ただし、少数の回答から固定的な能力ラベルや人格特性を作らない。

### P6. 不明点を不明のまま保持する

情報が足りない場合、Middle Mold は確信を捏造しない。未確認事項、評価不能な項目、追加で必要な観察を終了報告に残す。

## 4. 学習方式のカタログ

本モールドが扱うのは、学習科学で検討されてきた方式を基礎にした実務的な選択肢である。ここで列挙することは、どの方式もすべての課題に最適であるという主張ではない。

### 4.1 Diagnostic Check — 事前診断

**目的:** 既有知識、前提知識、誤概念、不確実な箇所を把握する。

手順：

1. 目標に対応する短い説明、予測、または代表問題を提示する。
2. 正しい理解、偶然の正答、推測、未理解を可能な範囲で分ける。
3. 結果に応じて説明量と足場かけを調整する。

注意点：

- 1問の結果だけで能力全体を決めない。
- 診断を高圧的な評価にしない。
- 分からないという回答を、人格や努力の評価に変換しない。

### 4.2 Worked Example — 例題学習

**目的:** 初学者が複雑な課題に取り組む際、何をどの順序で行うかを具体的に示す。

手順：

1. 解答例を示す。
2. 重要な手順ごとに理由を説明する。
3. 途中の判断点を明示する。
4. 次の例題では学習者が一部の手順を担当する。

例題を見せ続けるだけでは、独力での遂行を確認できない。必ず後続の自力演習と組み合わせる。

### 4.3 Guided Practice — ガイド付き練習

**目的:** 例題から独立遂行への移行を支援する。

手順：

1. 類似課題を提示する。
2. すぐに答えを渡さず、次の手順や判断を質問する。
3. 必要に応じて部分的なヒントを出す。
4. 学習者が進めるようになったら、ヒントを段階的に減らす。

ヒントを減らすのは、単に時間が経過したからではなく、実際の遂行結果に基づいて判断する。

### 4.4 Retrieval Practice / Active Recall — 想起練習

**目的:** 資料を見直すだけでなく、記憶から知識や手順を取り出す練習を行う。

手順：

1. 説明や資料をいったん隠す。
2. 要点の説明、手順の再構成、短い問題への回答を求める。
3. 回答を基準と照合する。
4. 不足を修正し、必要なら別の例で再確認する。

初めて学ぶ複雑な内容に対して、十分な説明を行う前から全面的な想起を要求しない。

### 4.5 Spaced Practice — 分散学習

**目的:** 一度の集中学習だけで終わらせず、時間を空けて再度取り出す機会を作る。

手順：

1. 初回学習の後に短い復習を計画する。
2. 復習では最初に想起または実演を行う。
3. 成績と誤りに応じて次の間隔を調整する。
4. 期限が近い場合は、残り時間に合わせて優先順位を調整する。

復習間隔は固定の万能値ではない。課題、保持期間、期限、学習者の結果に合わせて調整する。

### 4.6 Interleaving / Contrastive Practice — 交互配置・対比練習

**目的:** 類似した概念、問題形式、手順の中から適切なものを選ぶ力を鍛える。

手順：

1. それぞれの基本手順を先に学ぶ。
2. 異なるタイプの問題を混ぜて提示する。
3. どの手順を選ぶか、その判断根拠を説明してもらう。
4. 判別に失敗したら、必要に応じて個別の手順練習へ戻る。

初学段階で基礎手順そのものが成立していない場合、交互配置を強制しない。最初は同じ型をまとめて練習する方が適切な場合がある。

### 4.7 Self-Explanation — 自己説明

**目的:** 答えを出すだけでなく、なぜその手順や結論が成立するかを説明する。

質問例：

- なぜこの手順を使うのか。
- どの条件が変わると結論が変わるのか。
- この説明を支える規則や証拠は何か。
- 反例を作るとしたら、どの条件を変えるか。

流暢な説明だけで理解を認定しない。新しい例題や反例への対応で確認する。

### 4.8 Specific Corrective Feedback — 具体的な修正フィードバック

**目的:** 間違いを、次に何を直せばよいか分かる情報へ変換する。

基本形式：

1. どの手順・主張・判断に問題があるかを特定する。
2. なぜ問題なのか、または何の根拠が不足しているかを説明する。
3. 必要最小限の修正例を示す。
4. 学習者に再試行してもらう。
5. 表面だけ異なる新しい問題で転移を確認する。

「違う」「もっと頑張る」だけのフィードバックは避ける。正解・不正解のラベルだけで終わらせない。

### 4.9 Error-Pattern Review — 誤りパターンの確認

**目的:** 過去に観察された誤りを分類し、修正対象を選ぶ。

例：

- 前提知識の欠落
- 概念の取り違え
- 手順の抜け
- 計算・操作上のミス
- 問題タイプの誤分類
- 根拠のない仮定
- 検算・確認の欠落

誤りを本人の固定的な性質として扱わない。観察できた行動として記録し、少数の事例から一般化しない。

## 5. 方法選択ルール

Middle Mold は、目的と入力シグナルから手順を構成する。現行の Python 実装は単純なヒューリスティックであり、学習方法を自動的に最適化する検証済みアルゴリズムではない。

| 条件 | 選択の基本方針 |
|---|---|
| 現在の習熟度が不明 | 診断を最初に置く |
| 初学者・未知の課題 | 例題とガイド付き練習を厚くする |
| 独力での再現が目標 | 想起練習と独立チェックを含める |
| 長期保持が必要 | 分散復習を計画する |
| 類似カテゴリの判別が必要 | 基本手順の学習後に交互配置を検討する |
| 概念理解・問題解決が中心 | 自己説明を含める |
| 具体的な誤り履歴がある | 誤りパターンの確認を追加する |
| 前提知識が不安定 | 複雑さを上げる前に前提を確認する |
| 期限が非常に近い | 代表問題、想起、重要エラーの修正を優先する |
| 期限に余裕がある | 分散復習と転移課題を含める |

選択規則は「有効な手法をすべて常に実行する」というものではない。現行実装では診断、例題から自力演習への移行、想起、フィードバック、分散復習を基本セットとし、交互配置や自己説明などは課題の信号に応じて調整する。

## 6. セッション構造

標準的なセッションは次の5段階で構成する。

### S1. Diagnose — 現在地を確認する

- 目標に対応する短い課題を提示する。
- 正答、誤り、推測、不明点を区別して記録する。
- 前提知識の不足があれば、必要最小限の前提学習を検討する。

### S2. Explain and Model — 説明と例示

- 目標に必要な範囲に絞って説明する。
- 重要な判断点を含む例題を示す。
- 例題の各手順が成立する理由を明らかにする。

### S3. Guided Practice — 支援付きの練習

- 類似した課題を学習者自身に進めてもらう。
- 必要に応じてヒントを出す。
- 同じ説明を繰り返すだけで進まない場合は、表現・例・前提確認を変更する。

### S4. Retrieve and Correct — 想起と修正

- 資料を隠した状態で要点や手順を再現してもらう。
- 観察された誤りを具体的に説明する。
- 修正後、別の表面例で再試行する。

### S5. Independent Check and Exit Report — 独立確認と終了報告

- ヒントなしの新しい課題で確認する。
- 成功、部分成功、未確認を区別する。
- 未解決事項、次の復習候補、必要な追加データを記録する。

時間が足りない場合は、例題数や説明量を減らす。独立確認と終了報告を安易に削除して、学習成果を確認しないまま「完了」としない。

---

## 7. 適応ルール

Middle Mold は固定スクリプトではなく、観察結果に応じて局所的に手順を変更する。

1. **前提不足:** 本題を一時停止し、最小限の前提知識を確認・補完する。
2. **同じ理由で2回続けて失敗:** 同じ説明をそのまま反復するのではなく、表現・例題・分解単位を変更する。
3. **異なる例題で独力成功が安定:** ヒントを減らし、転移距離を少し広げる。
4. **答えは正しいが説明に根拠がない:** 根拠、導出、反例を確認する。
5. **速いが誤っている:** 速度向上ではなく、誤りの原因特定を優先する。
6. **時間不足:** 例題数を減らしても独立確認を残す。
7. **判断材料不足:** 不明点として記録し、断定を避ける。
8. **一時的な失敗:** 固定的な能力ラベルや人格特性へ変換しない。
9. **自信と成績の不一致:** 自信を正答の代替にせず、次の診断に利用する。
10. **交互配置で混乱が増える:** 一時的に課題を分けて練習し、基礎が成立してから再び混合する。

## 8. 評価契約

評価は「学習者が分かったと言ったか」だけで決めない。目的に対応する観察可能な基準を設定する。

### 8.1 Objective Alignment

- **確認方法:** 回答・実演を目的の構成要素と照合する。
- **合格条件:** 必須要素を実際に示している。
- **未達時:** 欠けている要素を一つに絞って補完する。

### 8.2 Independent Retrieval / Performance

- **確認方法:** ヒントや資料なしで、新しい課題に回答する。
- **合格条件:** 実質的なヒントなしで成立し、必要に応じて主要な理由・規則を説明できる。
- **未達時:** 最小限の支援を戻し、修正後に類似課題で再確認する。

### 8.3 Error Correction

- **確認方法:** 修正した誤りを、別の表面例で再テストする。
- **合格条件:** 同じ根本原因の誤りが再発しない、または残存する不確実性が明示されている。
- **未達時:** 誤りを分類し、焦点を絞った練習に戻る。

### 8.4 Confidence Calibration

- **確認方法:** 学習者の自信を記録し、実際の成績と別々に保持する。
- **合格条件:** 自信と正答率・遂行結果が混同されていない。
- **未達時:** 差異を次の診断に利用する。自信を習熟の証拠として扱わない。

この評価契約は、すべての教科・技能で同じ採点尺度を使うという意味ではない。各 Purpose Program / Domain Content が、具体的な正答基準や実演基準を与える必要がある。

## 9. 入出力契約

### 9.1 入力: `LearningRequest`

主なフィールド：

| Field | 意味 |
|---|---|
| `objective` | 観察可能な学習目標 |
| `task_type` | 概念、手続き、事実、問題解決、混合、未知 |
| `current_proficiency` | 現在の習熟度の暫定推定 |
| `deadline_days` | 期限までの日数。未定なら `None` |
| `available_minutes` | セッションに使える概算時間 |
| `prerequisite_stability` | 前提知識が安定しているか |
| `categories_to_discriminate` | 類似カテゴリや手順の判別が必要か |
| `error_history` | 観察済みの具体的な誤り |
| `desired_mastery` | 到達状態の説明 |
| `context` | 追加のタスク情報。人格指示は入れない |

### 9.2 出力: `LearningPlan`

- `selected_methods`: 選択された手法、理由、手順、注意事項
- `steps`: セッションの順序、学習者の行動、LLM の行動、完了シグナル
- `evaluation`: 目標との対応、独立遂行、誤り修正、自信の記録
- `adaptation_rules`: 観察結果に応じた変更条件
- `limitations`: この計画で断定できないこと
- `exit_report_fields`: 終了時に報告する項目
- `evidence_notes`: 手法の根拠に関する注意書き

### 9.3 BOTTOM LLM に対する実行規約

BOTTOM の LLM は次を守る。

1. `objective` と評価条件を保持し、対話中に勝手に変更しない。
2. Persona Seed の口調・説明スタイルは利用してよいが、学習目標や正答条件を改変しない。
3. 実施していない診断、提示していない問題、観察していない成績を報告しない。
4. 学習者の誤りを人格評価に変換しない。
5. 不明な点を不明として残す。
6. 選択した方法が課題に合わないと分かった場合、その理由と変更を記録する。
7. 例題や問題を生成する場合、Domain Content の正答基準と整合させる。
8. 「説明を読んだ」「うなずいた」「正解を見た」を、独立遂行の証拠にしない。
9. 終了時に `exit_report_fields` を満たす。取得できない項目は未取得と明示する。
10. このモールド自体を実験的に評価する場合、個々の学習成果とモールド全体の有効性を分けて検証する。

## 10. 終了報告フォーマット

実行する LLM / アプリケーションは、少なくとも次の情報を返す。

```text
EXIT_REPORT
- objective:
- steps_completed:
- independent_recall_or_performance:
- errors_observed:
- corrections_completed:
- confidence_rating:
- next_review_recommendation:
- unresolved_unknowns:
```

推奨される記録規則：

- 観察した事実と推定を分ける。
- 未実施の手順を実施済みとして扱わない。
- 成功・部分成功・未確認を区別する。
- 学習者の同意や自己申告だけで習熟認定しない。
- 次の復習日時は、期限や実際の成績が分かる場合にのみ具体化する。
- 個人情報を必要以上に保存しない。

## 11. Python 実装

`middle_mold.py` は、上記の契約を Python のデータクラスと `MiddleMold` クラスとして表現する。

### 11.1 実行

Python 3.10 以降を想定する。標準ライブラリ以外の依存関係はない。

```bash
python middle_mold.py
```

実行すると、因数分解の学習を題材にしたサンプル `LearningPlan` が JSON で標準出力に表示される。

### 11.2 呼び出し例

```python
from middle_mold import (
    MiddleMold,
    LearningRequest,
    TaskType,
    Proficiency,
)

request = LearningRequest(
    objective="説明を見ずに、対象形式の因数分解を正しく行い、選択理由を説明する。",
    task_type=TaskType.PROBLEM_SOLVING,
    current_proficiency=Proficiency.NOVICE,
    deadline_days=60,
    available_minutes=30,
    categories_to_discriminate=True,
)

plan = MiddleMold().build_plan(request)

print(plan.to_json())
```

### 11.3 実装上の境界

この Python ファイルは、学習計画を組み立てるプロトタイプであり、次の機能は実装していない。

- LLM API 呼び出し
- 会話履歴の永続化
- 学習者の長期プロファイル保存
- 教材データベース
- 正答判定器
- 復習通知のスケジューラ
- 実験データの集計・統計検定
- Persona Seed / Purpose Program の完全な統合ランタイム

これらを必要に応じて外部モジュールとして接続する。特に、個人化の情報をこのモジュールへ直接埋め込まず、入力契約と出力契約を介して接続することを推奨する。

## 12. エビデンスと限界

Middle Mold は学習科学の研究で扱われている方式を参考にしているが、ここに示す実装全体が研究で検証済みという意味ではない。方法の一般的な支持と、この組み合わせ・実装・対象集団での効果は区別する必要がある。

## 13. 検証計画

Middle Mold を「それらしい設計文書」で終わらせず、実用性を評価するために次の段階を推奨する。

### Phase A — Contract Validation

- 必須入力が欠けている場合に明示的なエラーが返る。
- 出力に手法選択理由、手順、評価、適応、限界、終了報告項目が含まれる。
- 同一入力に対して同じ計画が生成される（決定論的な計画生成）。
- Persona Seed の有無で学習目標や評価契約が変化しない。

### Phase B — Execution Fidelity

- LLM が計画に含まれる段階を実際に実行したか記録する。
- 計画されたが未実施の手順を区別する。
- フィードバックが誤り箇所と次の行動を具体的に示しているか評価する。
- 終了報告に捏造された観察結果が含まれないか確認する。

### Phase C — Learning Outcome

可能な範囲で比較条件を設定する。

- Baseline: 通常の自由形式の学習支援
- Middle Mold: 本モールドを使用した学習支援

主な評価候補：

- 直後テストの正答率
- 遅延テストでの保持
- 未見問題への転移
- 必要なヒントの量
- 同一誤りの再発率
- 学習時間あたりの達成度
- 学習者の自信と実際の成績の差

可能なら課題・時間・事前知識を揃える。少数の事例から因果効果を断定しない。実験設計、サンプル数、採点基準を事前に決める。

### Phase D — Ablation

各要素を外した条件を比較する。

- 想起練習なし
- 分散復習なし
- ガイド付き練習なし
- 明示的な評価契約なし
- Persona Seed と Middle Mold を混在させた条件

この比較により、どの要素がどの結果に寄与しているかを調べやすくなる。ただし、要素間の相互作用があるため、単純な差分だけで全体の因果構造が確定するわけではない。

## 14. 既知の課題と次の設計判断

### 課題 1: 学習方法の選択が単純なヒューリスティック

現行実装は、課題タイプや入力フラグに基づいて方法を選ぶ。課題の詳細な構造や実際の成績に基づく高度な選択器ではない。

**次の候補:** Domain Adapter が、課題の型・必要な認知操作・典型的な誤りを構造化して渡す。

### 課題 2: 習熟度が自己申告や初回回答に依存しやすい

習熟度の推定は不確実である。初回診断はあくまでサンプルであり、継続観察による更新が必要。

**次の候補:** 観察ログと評価器を独立させ、観察された証拠と推定された習熟度を別々に保存する。

### 課題 3: 分散復習の時刻を決める機能がない

現行コードは復習を計画項目として提示するだけで、通知や実行を管理しない。

**次の候補:** 外部の Scheduler が、期限・成績・ユーザーの利用可能時間から復習タスクを生成する。

### 課題 4: 教科固有の正答基準がない

Middle Mold は教科内容を所有しないため、正答判定や採点基準は Domain Content / Purpose Program 側が提供する必要がある。

**次の候補:** `EvaluationAdapter` のようなインターフェースを設け、数学・語学・技能訓練などの判定器を接続する。

### 課題 5: Persona Seed との境界を維持する必要がある

Persona Seed が学習者に合う説明表現を選ぶことは許容される。一方、評価条件や未達成の扱いを個性に合わせて改変すると、学習プロセスの比較可能性が失われる。

**次の候補:** Persona は presentation parameters のみを変更し、Middle Mold の objective / evaluation / evidence fields は不変とする契約テストを追加する。

## 16. 最終的な位置づけ

Middle Mold は、個性を作る仕組みではなく、学習の進め方を安定して構成する共通プロセス層である。

- **Persona Seed:** 誰に、どのような対話上の適応を行うか。
- **Purpose Program:** 何を、いつまでに、どの基準で達成するか。
- **Middle Mold:** どの学習方法を、どの順序と条件で使うか。
- **BOTTOM LLM:** それらの契約を、実際の対話・説明・練習・記録として実行する。
- **Domain Content / Evaluator:** 具体的な教材と正答基準を供給する。

この分離により、学習対象や人格設定を変更しても、共通の学習プロセスを再利用しやすくなる。ただし、再利用可能であることと、すべての用途で効果が保証されることは別である。実際の有効性は、明示的な評価基準と比較検証によって確認する。
